# Fiber와 Concurrent Rendering

## 정의


<toggle>
<b>React Fiber란 무엇이고, 왜 도입되었나요?</b>

기존 리액트는 동기적으로 작업이 진행되어서 작업이 시작 후 메인스레드를 점유할 경우 작업 중간에 우선순위가 높은 사용자 입력이 들어올경우 사용자 입력 처리가 지연될수있습니다. 이러한 작업을 쪼개고 우선순위가 높은 작업을 중간에 실행할수있도록 작업의 상태를 관리하는 것이 리액트 피버 아키텍처의 역할입니다.
</toggle>

<toggle>
<b>Concurrent Rendering이란 무엇이며, 기존 렌더링 방식과 어떤 차이가 있나요?</b>

기존 렌더링 방식은 동기적으로 렌더링이 진행되어, 무거운 렌더링 진행이 동기적으로 진행될경우, 다음 우선순위가 높은 작업이 들어와도 진행되고 있는 작업을 끊지 않고 작업이 완료될때까지 기다려야했습니다. 하지만 동시성 렌더링 concurrent Rendering은 우선순위가 높은 렌더링 작업이 들어왔을때, 작업을 진행할 수 있도록 우선순위에 따라 작업을 수행할수있는 것에 차이가 있습니다. 이때 중단할 수 있는것은 리액트의 핵심 3과정 중 렌더단계이며, commit 단계는 동기적으로 진행됩니다.
</toggle>

<toggle>
<b>React가 렌더링을 진행하는 도중 더 높은 우선순위의 업데이트가 발생하면 어떻게 처리하나요?</b>

React는 우선순위가 높은 업데이트가 발생하면 진행 중인 낮은 우선순위의 렌더링을 중단하고 긴급한 업데이트를 먼저 처리할 수 있습니다. 중단된 렌더링은 이후 재개하거나 폐기할 수 있으며, 최종적으로 완료된 결과만 Commit 단계에서 실제 DOM에 반영됩니다.
</toggle>

<toggle>
<b>React의 </b>startTransition<b>은 어떤 상황에서 사용하며, 사용자 경험을 어떻게 개선하나요?</b>

startTransition은 긴급하지 않은 state 업데이트를 전환 작업으로 지정할 때 사용합니다. 예를 들어 검색창에 입력한 내용을 즉시 반영하면서, 검색 결과 목록을 갱신하는 렌더링은 낮은 우선순위로 처리할 수 있습니다. 이를 통해 무거운 목록 렌더링 중에도 사용자 입력의 응답성을 유지하는 데 도움을 줄 수 있습니다.
</toggle>

## 특징


- <b>05 왜 React가 렌더링 작업을 나누고, 어떤 작업을 먼저 처리할 수 있는지 이해하는 단계</b>
- Fiber란, 리액트 재조정 아키텍처 : 컴포넌트별 작업과 상태 등을 표현하는 내부 노드 구조
- Concurrent Rendering이란, Fiber에서 관리되는 렌더링 작업을 상황에 따라 중단하거나 진행하거나 폐기할 수 있다.
  <ul>
  <li>
  특징 : <b><u>작업의 우선순위를 조정</u></b><b>하고, </b><b><u>중단 가능한 렌더링</u></b><b>을 통해 긴급한 작업을 먼저 실행할 수 있다.</b>
  </li>
  <li>
  JavaScript가 여러개의 작업을 동시에 여러 스레드에서 일할수있다는 것은 아니다. 
  </li>
  <li>
  React 16에서 도입했고, 18에서 startTransition과 같은 동시성 기능이 정식으로 제공되기 시작함.
  </li>
  </ul>

<ol>
<li>
더 긴급한 업데이트 요청이 들어오면, 우선순위에 따라 진행중이던 렌더링 작업을 중단하거나 폐기할수있다.
</li>
<li>
폐기된 렌더링 작업은 커밋되지 않기 때문에, 실제DOM에 반영되지 않는다. 
</li>
</ol>
</li>

#### Scheduler와 업데이트 우선순위

<ul>
<li>
startTransition : 특정 state 업데이트(setQuery 등..)를 <b>긴급하지 않은 전환 작업</b>으로 표시할 수 있다. 

- 작업의 우선순위를 낮추는 것
</li>
</ul>

```javascript
function handleChange(e) {
  const value = e.target.value;

  setInput(value); // 긴급: 검색창 입력값 갱신

  startTransition(() => {
    setQuery(value); // 비긴급: 검색 결과 갱신
  });
}
```

<ul>
<li>
작업 단위에서 제어권을 넘길 수 있도록 설계된 것. 따라서, 작업을 잘게 나눠야 중단할수있는 기회가 생긴다. 
</li>
<li>
Render : 동시성 렌더링에서는 작업의 중단,폐기,수정이 가능하다.
</li>
<li>
Commit : 확정된 변경사항은 <b><span color="red">동기적으로 반영</span></b>하며 중간에 중단이 불가능하다 
</li>
</ul>

#### 사용자 경험 개선

- 동시성 렌더링 : 사용자가 r 입력 → 목록 렌더링 → 다음 입력 반영
  - 무거운 작업을 동기적으로 실행한 이후 다음 입력을 반영한다.
- Concurrent Rendering : r 입력 → 목록 작업 중단 → re 입력 우선 → 목록 작업 재실행
  - 목록 작업을 진행 중임에도, 사용자 I/O 반응에 긴급한 입력을 우선적으로 반영한다.
  - 이때, ConcurrentRendering은 응답성을 좋게 만든다.
    <ul>
    <li>
    <b>응답성이란? </b>무거운 작업중에도 사용자의 반응을 얼마나 빠르게 반응할 수 있는지 
    </li>
    </ul>

## 실제 사용 예시(사례)


<ul>
<li>
 r에 대한 검색 결과를 렌더링하다가 사용자가 re를 입력했다고 했을때, 리액트 내부에서는 어떤 일이 일어날까?

<ul>
<li>
현재 진행중인 렌더링 보다 우선순위가 높은 작업이 들어왔을때, 진행중이던 렌더링은 중단하거나 폐기할 수 있다. 따라서 re의 입력 업데이트 요청을 반영하고, 기존 렌더링 중이던 r은 폐기하여 commit에 반영되지 않는다. 따라서 실제 dom노드에는 re만 반영된다. 
</li>
</ul>
</li>
</ul>
